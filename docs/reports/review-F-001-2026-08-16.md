## Failures in detail

### C1 / C2 — mobile is tagged on 24 ACs and implemented nowhere

One root cause, surfacing in two checks. These are **not** two independent defects.

The spec tags `mobile` on 24 of 29 ACs:

> AC-1, AC-2, AC-3, AC-4, AC-5, AC-7, AC-8, AC-9, AC-10, AC-11, AC-13, AC-14, AC-17, AC-18, AC-19, AC-20, AC-21, AC-22, AC-24, AC-25, AC-26, AC-27, AC-28, AC-29

Against that:

- `specs/assistant/F-001-voice-assistant-view.md:22` — `tested_by.mobile: []`
- `qa/assistant/F-001/mobile/` — directory does not exist (0 test cases)
- `src/assistant/mobile/` — does not exist (0 implementation files)
- `specs/_shared/platform/mobile.md` — exists, so the platform is specified but never built

**AC-26 and AC-27 are mobile-only** (`(mobile)` is their sole tag): backgrounding/kill while listening, and while thinking. Nothing in this feature verifies them on any platform — they are the two ACs with zero coverage anywhere, not merely zero mobile coverage.

The briefing states mobile was never in scope for F-001 and that this is a web-first phase. That is consistent with what is on disk, but **the spec does not say it**: `## Out of Scope (this iteration)` lists 7 deferrals and mobile is not among them. So the artifact that C1/C2 read as authoritative still promises mobile.

Suggested fix — a spec edit, not an implementation task. Pick one:
1. Retag the 24 ACs to `(api, web)` and add "**Mobile (React Native) surface** — deferred to F-00N; the AC set is unchanged, only the platform tags move" to `## Out of Scope`; move AC-26/AC-27 wholesale to that follow-up feature. This makes the green suites honestly complete.
2. Keep the tags and accept F-001 as knowingly partial, with a mobile task queued before sign-off.

Option 1 matches what was actually built. Either way the decision is the human's.

### C8 — no `## Ops` section

- `specs/assistant/F-001-voice-assistant-view.md` — section absent entirely. Sections present: Links, Purpose, Users & Permissions, Conversation model, User Flow, Acceptance Criteria, Data, API Touch Points, Test strategy, Coverage of existing UCs, Out of Scope, Open Questions.
- `Links.api_endpoints` (line 18) declares 8 endpoints, so C8's "no API endpoints → WARNING" relief does not apply.

The briefing notes that "N/A with justification is legitimate if the spec says so" for a prototype phase — but the spec says nothing, and empty is explicitly not legitimate. This is the cheapest failure on the list to clear.

Suggested fix — add to the spec:

```markdown
## Ops

- **Observability** — turn outcome counter by `turn.outcome.kind`; undo refusal
  counter by `detail.reason`. Prototype: in-process counters, no exporter (ADR-001).
- **Rollback criteria** — N/A this phase: prototype server, no deployment target
  and no live users to roll back for.
- **Feature flag** — N/A: F-001 is the app's main view, not an increment behind a flag.
```

Two of the three are legitimately N/A here; only the observability line asserts something new, and the counters it names already exist implicitly in the harness AI-call counter pattern.

### C9 — three documentation/implementation mismatches

**C9.1 — `500 INTERNAL` is emitted but documented nowhere**

- `src/assistant/api/app.ts:362` — `json(res, 500, { error: { code: 'INTERNAL', message: 'internal error' } })`
- `specs/assistant/api-contracts.md` — `INTERNAL` appears in no error table; the only documented 500 is `APPLY_FAILED`.

This is the catch-all for a non-`ApiError` throw. The code is correct (it deliberately avoids leaking stack traces); the contract simply never recorded it. Fix: one row in `## Conventions` — "Any unhandled server fault → `500 INTERNAL`, no detail, stack traces never leaked."

**C9.2 — two persisted `assistant_session` fields are absent from data-model.md**

`specs/assistant/data-model.md:29-38` lists 8 fields for `assistant_session`. The implementation persists two more:

- `src/assistant/api/types.ts:162` — `boundary_late: BoundaryLateOutcome[] | null`. **This one reaches the wire**: `engine/serialize.ts:158` emits it as `Boundary.late_outcomes`, which `api-contracts.md:189` documents on the response but which has no backing entity field in the data model. AC-28 requires exactly this data ("any turn that resolved between last foreground and close").
- `src/assistant/api/types.ts:166` — `last_foreground_at`, internal and correctly stripped from the wire.

Fix: add both rows to the `assistant_session` table. `last_foreground_at` should carry the approximation note in C9.3's terms.

**C9.3 — the AC-7 modified-since baseline in the contract is not what the code does**

The spec and the contract both state the comparison baseline is the **pre-apply** snapshot:

- `specs/assistant/F-001-voice-assistant-view.md:86` (AC-7) — "a task counts as modified iff its current state differs from the `turn.undo_snapshot` entry captured at apply"
- `specs/assistant/api-contracts.md:238-239` — "a task is skipped iff its current state differs from the `undo_snapshot` entry captured at apply"

The implementation compares against **post-apply** state:

- `src/assistant/api/engine/undo.ts:71` — `const postApply = turn.post_apply ?? {}`
- `src/assistant/api/engine/undo.ts:78` and `:97` — `if (cur !== undefined && taskEquals(cur, expected))` where `expected = postApply[id]`
- `src/assistant/api/types.ts:126-129` — "undo's modified-since comparison is current-vs-post-apply (AC-7 — comparing against the pre-apply snapshot would flag the turn's own change as a modification)"

**The code is right and the documents are wrong.** Comparing current state against the pre-apply snapshot would mark every task the turn itself changed as "modified since", so undo would skip everything it had just applied and always return `nothing_reverted: true`. The literal contract sentence describes an undo that can never revert anything.

The briefing flags this as a declared prototype tradeoff. It is not really a tradeoff — it is a spec defect that the implementer worked around correctly and recorded only in a code comment. Fix: correct AC-7's sentence and `api-contracts.md:238-239` to name post-apply state as the baseline. Left as-is, the next implementer or QA author reads the contract, calls the code a bug, and "fixes" working behaviour into a broken state.

## Caveats on passing checks — what did *not* get verified

Recorded because a check that skipped is not a check that passed.

- **C11**: 6 of 24 assertions skipped. `tokens.json` declares no breakpoints, so overflow was checked at the browser default (1280px) only — no narrow-viewport verification on any of the 3 mockups. `DESIGN.md` states no target contrast ratio, so **contrast was not measured** on any mockup. AC-19 names WCAG **1.4.3 (contrast)** by name, so the one automated check that could have covered it did not run.
- **C12**: the first web run reported FAIL, but all 4 of its mutations landed in `main.tsx`, `seams.ts`, and `vite.config.ts` — browser bootstrap, test-seam wiring, and build config, none of which the unit suite is meant to cover. The attempt budget was exhausted before reaching any behavioural file. Re-run against the behavioural core (`model/reducer.ts`, `model/messages.ts`, `controller.ts`, the three components), the suite detected a break on mutation 1. Recorded as PASS on the second run; the first is inconclusive, not a finding.
- **C14**: `testid-contract.sh` reported 3 missing (`assistant-chip-affirm`, `assistant-chip-negative`, `assistant-option-chip`). All three are present at `src/assistant/web/components/ConversationPane.tsx:130-136`, applied through a multi-line JSX ternary the tool's single-line regex cannot read. Disproved behaviourally: `src/assistant/web/__tests__/app.test.tsx:310` parses the mockup catalogue, asserts it holds 22 ids, renders all 17 states, and requires both `missing` and `invented` to be empty — it passes. Marked PASS on the rendered-DOM evidence, which is the stronger observable.
- **C12 tooling hazard**: `suite-can-fail.sh` restores mutated files with `git checkout --`, which cannot restore an **untracked** file. Nothing in this repo is committed, so the API run left `src/assistant/api/errors.ts` mutated on disk. Caught by a pre-run checksum manifest and restored from an out-of-tree backup; the tree was verified byte-identical afterwards and both suites re-run green. See `specs/_shared/LEARNINGS.md` L-001.
