## The design→implementation contract — verified by falsification

The briefing asked me to check this specifically, and it is the strongest thing
in this feature.

`permissions.test.ts:64-78` reads `design/_shared/components.md` at test time and
parses the § MicControl permission table into a `Map<rowId, {head, body, cta}>`.
The eight row IDs are then asserted individually — head, first body line, and CTA
label — against `permissionCopyRow(id)` in the implementation. There is no
transcribed expectation anywhere in the file for those strings.

**I did not take this on trust.** I checksummed `design/_shared/components.md`,
inserted the token `MUTANT` into the `IOS-MIC-UNASKED` body, and re-ran:

```
× IOS-MIC-UNASKED is quoted verbatim from design/_shared/components.md
× every enumerated tuple selects its catalogue row
× mic denied + speech undetermined is IOS-MIC-UNASKED, and claims no grant the user never gave
× no message body is derived — every published body appears literally in the model
  AssertionError: IOS-MIC-UNASKED is not a literal in permissions.ts

Tests  4 failed | 37 passed (41)
```

Restored byte-identical (`cksum` 4262931886 15922 before and after), re-ran:
**41 passed (41)**.

Three properties make this stronger than an ordinary assertion:

- **It fails when the upstream artifact moves.** Every other cross-artifact check
  in this repo compares two things the *implementation* controls. This one breaks
  if design edits its own file, which is the direction drift actually travels.
- **It forbids derivation, not just mismatch.** The test named in the failure
  above reads `permissions.ts` as text and requires every published body to
  appear as a **literal**. That is the assertion that made the eighth iOS tuple
  visible: an interpolating template satisfies "the string matches" while
  silently generating plausible copy for combinations nobody enumerated.
- **It pins the reasoning, not only the strings.** `IOS-MIC-UNASKED does NOT
  promise that the mic alone restores the feature` asserts that this row omits
  the closer every *other* denial row carries — encoding *why* the row differs,
  so a future edit that "harmonises" the copy fails instead of quietly lying to a
  user whose speech permission was never asked.

The downstream story checks out too. `deniedRowFor('ios', {microphone:'granted',
speech_recognition:'undetermined'})` renders **no message at all**, and iOS
routes every denial to `settings` — both asserted, and both are the live bug the
briefing describes (a partial grant was rendering IOS-SPEECH, telling the user
they had switched off a permission they were never offered).
