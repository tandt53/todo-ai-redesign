## Part 1 — What was decided today, in order

Four owner decisions reshaped the task model in one day. **Each was correct when
taken**; do not read the sequence as churn, and do not re-litigate any of them.
Every one has a report in `reports/`.

### 1. Four collections instead of three (`owner-decision-2026-08-18-four-buckets.md`)

`Today · Upcoming · Inbox · Done`. The owner's question was *"I thought Inbox and
Today were just due-date filters, why is this so complicated?"* — and they were
right: Today was a date filter and Inbox was a status filter, two different
kinds. **The complexity was the symptom of a missing bucket.**

### 2. Overdue stays in Today (`owner-decision-2026-08-18-four-buckets.md`, second pass)

The owner raised moving overdue to Inbox — cleaner on paper, dissolves three
problems — and **declined it** in favour of keeping missed work where they
actually look. Recorded explicitly so nobody re-argues it on the grounds that the
tidier option was overlooked. Today therefore means *"needs attention now"*, not
literally *"dated today"*.

### 3. Inbox is **unfiled**, not **undated** (`owner-decision-2026-08-18-inbox-is-unfiled.md`)

The owner asked how other apps keep an Inbox. In Todoist, Things, TickTick and
OmniFocus it is a **container you empty by filing**, never a date filter — and a
task sits in Inbox *and* in Today at once, because one is a place and the other
is a view.

**This is the most important structural fact in the codebase right now.** The
model is **two axes**: a date axis (Today · Upcoming · undated) and a filing axis
(Inbox · each personal list), with Done the gate that empties both. `ADR-009
§ Amendment 2` is the authority.

`lists` and `tasks.list_id` do not exist, so nothing can be filed, so **Inbox is
every open task today** — and narrows by itself when lists ship.

> **The trap, named `INV-INBOX-FILING`:** `open_all` and `inbox_count` are
> **exactly equal today**, at 716, in all 193 accounts. They will diverge the
> moment lists ship. Nothing in the data looks like a coincidence, so someone
> will notice the equality and re-merge them — reintroducing the bug the split
> fixed, which tells a user with a full week ahead that their list is clear.
> **They are two facts. Do not merge them.**

### 4. Creating on Upcoming saves dateless and says so (`owner-decision-2026-08-18-upcoming-create.md`)

Upcoming is not one day, so no date is derivable. The task is created dateless,
lands in Inbox, and a **SaveNotice** says where it went. Design refused to make
it a toast, for a reason worth keeping: on Upcoming the backdrop looks identical
before and after the save, so a message that times out **re-creates the silence
it exists to end, four seconds later.**

### 5. F-005 Gate 1 — four more (`owner-decision-2026-08-18-f005-gate1.md`)

Reminders shown when the app opens · mobile web-first with the shared-model leaks
plugged · the four value fields reachable by voice, structure hand-only · the
row's delete gains the undo it never had.

### The template was upgraded on 2026-08-18 — what arrived and what did not

`upgrade-project.sh` ran, 88 files updated. It brought three things worth knowing:

- **spec-agent now owes an `## Impact` section** on any feature that is not the
  first in its module, and **Gate 1 reviews it under every lens**, with a missing
  section a HIGH finding. T-143 no longer needs that carried by hand.
- **The memory system has a writer.** `ORCHESTRATION.md` Step 5.8 records
  `memory_entry:` / `agent_memory_entry:` from every return. Before this, every
  agent read four memory layers that returned empty **forever**, because the sole
  writer was never told it was the writer. `memory/` is seeded rather than empty —
  an empty file teaches agents to stop reading.
- **C14 recognises `resource-id`** and no longer accepts an id parked in
  `contentDescription`. This project had the fix locally and the template did not;
  it was ported upstream **before** the upgrade, so the upgrade did not revert it.

**MANIFEST is preserved by the upgrade by design**, so the three `memory*` paths
were added here by hand. Anything else the template adds to MANIFEST will need
the same treatment.

### R9 was red, and fixing it uncovered a second bug underneath

Resolved the same day — recorded because the shape is worth knowing.

`package.json` declares `"type": "module"` and four template files used CommonJS
in `.js` files, so Node threw on load: the node task reader was dead while the
shell reader worked. Fixed upstream by renaming them `.cjs` and delivered here by
`upgrade-project.sh`, which now also removes the superseded `.js`.

**Then R9 ran properly for the first time and immediately failed differently** —
111 rows against 109. The node reader matched `T-\d+`, which matches `T-070` and
not `T-070b`, so **the dashboard had been silently omitting every lettered
sub-task** the orchestrator was acting on. Two defects stacked: a check that
could not run, hiding a defect it existed to catch.

Worth carrying: the same pattern bit an archival script in this project on the
same day, moving every numbered row to the archive and leaving its lettered
children behind — eleven rows recovered from git. **`T-\d+` is a known hazard in
this queue.** Match `T-\d+[a-z]?`.
