## Failures in detail

### C5 — the declared automation suites have never run

`Links.tested_by` names four entries. The two TC-markdown directories are real and well-formed (40 api + 32 web files). The two **automation** entries do not execute.

**C5.1 — api automation: 46 of 46 tests fail**

```
qa/assistant/automation/api/F-001-voice-assistant-view.spec.ts:105
  const { createMemoryStore } = require('../../../../src/assistant/api/store/memory');

Error: Cannot find module '../../../../src/assistant/api/store/memory'
```

Three independent defects in one line:

- the module is `src/assistant/api/store/memory-store.ts`, not `store/memory`;
- `createMemoryStore` **is not defined anywhere in `src/`** — the real export is the class `MemoryStore` (`memory-store.ts:17`);
- `require()` is used inside a `"type": "module"` ESM project.

Every test fails in `makeHarness` before touching the app, so all 46 fail identically. The line's own comment — *"Memory store construction per backend.md store/ layout; align imp…"* — records that it was written against an assumed layout. It was never run against the real one.

**C5.2 — e2e automation: 0 tests collected**

```
Error: Cannot find package '@playwright/test' imported from
  qa/assistant/automation/e2e/F-001-voice-assistant-view.spec.ts:19
```

`@playwright/test` is absent from `package.json` and from `node_modules`, and there is **no `playwright.config.*` anywhere in the project**. This suite cannot run by any command, not merely by the wrong one. (`npx playwright --version` resolves a globally-cached binary; that is not a project dependency and changes nothing.)

**Why the prior review missed it.** My last pass ran the two platform-doc commands (`vitest run src/assistant/api`, `vitest run src/assistant/web`) and reported their sum, 167, as C5's evidence. Both are green and both are honest — but they cover `src/**` only. The project's own aggregate command, `npm run test:all` (`vitest run`, no path), is **red**: `2 failed | 9 passed (11)`, `46 failed | 167 passed (213)`. A reviewer reporting "the test suite runs clean" while the feature's declared automation cannot import its own harness is reporting a false green.

**What this does *not* mean.** The 167 unit tests are real, and they cover the same ACs the automation targets — C2's P1 matrix is satisfied by the TC definitions, and C12 shows both unit tiers genuinely detect broken implementations. The exposure is that the automation tier claimed in `Links` is decorative, so nothing re-verifies these ACs the way the spec says they are re-verified.

### C9.4 — four persisted turn fields are absent from data-model.md

Same defect class as C9.2, one entity over. `TurnRow` (`src/assistant/api/types.ts:103-136`) persists four fields that `data-model.md`'s `assistant_turn` table does not list:

| Field | types.ts | Written at | Drives |
|---|---|---|---|
| `post_apply` | `:128` | `engine/turns.ts:462` | **AC-7's modified-since baseline** |
| `created_ids` | `:131` | `engine/turns.ts:465` | AC-6 undo-of-create |
| `pending_op` | `:133` | `engine/turns.ts:603` | AC-13 clarify resolution |
| `caused_resolutions` | `:135` | `engine/turns.ts:318` | AC-16 dedupe replay of resolutions |

All four are initialised on every turn row (`turns.ts:294-297`), persisted in the store, and stripped on the wire by `serialize.ts` — the same shape as `last_foreground_at`, which the prior pass **did** flag and which the fix duly added. The convention is therefore already established and accepted; these four simply were not swept.

`post_apply` is the sharp one. C9.3 was an entire failure about naming the AC-7 comparison baseline correctly in prose — and the field that *implements* that baseline is still missing from the document that owns "what is persisted". `data-model.md` lists `undo_snapshot` as the turn's snapshot field and mentions post-apply state only in a parenthetical note on that row. An implementer rebuilding the store from the data model alone would produce a store that cannot support undo, clarify, or dedupe replay.

**This is pre-existing, not a regression** — none of the four fixes touched it, and my prior pass applied both-directions rigor to `assistant_session` but not to `assistant_turn`. Fix: four rows in the `assistant_turn` table, marked internal in `last_foreground_at`'s style.
