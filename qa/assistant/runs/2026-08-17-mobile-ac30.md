## 1. The red

`qa/assistant/automation/mobile/F-003-mobile-surface.spec.ts:207` asserted
`expect(sorted(ios)).toHaveLength(22)`. The catalogue now publishes 23 — design added
`assistant-new-message-affordance` for § NewMessageAffordance.

**Not changed to 23.** A hardcoded count is a second home for a fact the mockup already
owns (L-004), which is why the line went red for a legitimate addition instead of
following along. What the literal was standing in for is the thing the case now asserts
directly: that `catalogueOf()` **matched something**. Without that guard the three
equality assertions beneath it (`ios == android`, `mobile == web`) are vacuously green —
if the regexes stop matching, all three sets are empty and all three comparisons pass
while proving nothing. That is L-007's own defect, and it is the reason a count check
belongs there at all.

The case now parses the size, asserts it is non-zero, asserts the parsed set has that
size, and checks every value looks like a catalogue id rather than markup the regex
over-matched. The describe title and the file header lost their "22" for the same reason.

**Proved it can fail:** breaking `catalogueOf`'s attribute list so it matches nothing
turns this case red (along with 6 others). Restored byte-identical.

## 2. AC-30 coverage

New: `qa/assistant/automation/mobile/F-001-voice-assistant-view.spec.ts` (40 tests) and
`qa/assistant/F-001/mobile/` (9 TCs + index). F-001's `Links.tested_by.mobile` was empty
before this run.

**The rule every case is built around.** BUG-004 shipped because every existing test
asserted a message was PRESENT, never that it was VISIBLE — a message 176 units below the
fold satisfies all of them. So no case asserts a presence. Each asserts a number, a
comparison, or a distinction between two published states.

### Where each clause sits

**Falsifiable at the model tier** — (a)'s arithmetic including the three-viewport sample
and the before/after disagreement, (b)'s follow-and-clear, (c)'s hold-still as a strict
boolean plus the unchanged count, (d)'s aggregation of N arrivals into one control
carrying the total, (e)'s NMA-NEW/NMA-WAITING distinction with design's own literals and
the polite announcement including the NEW→WAITING transition, (f)'s two dismissal paths
plus the near-miss that keeps them honest, (g)'s three scroll paths each driven from its
own trigger, and (h)'s anchor on the user's own append driven against the real server.

**Only the device tier can falsify** — that a message is actually on screen, that the pill
overlays rather than reflows the pane, that the two-line clamp keeps the question legible
at 375, that a smooth scroll lands where it claims, that N arrivals paint exactly one
node, and that a tap on the pill scrolls. Enumerated step by step as TC-009, which is
**blocked**: `.mobile-app/shoot-sim.sh` publishes 17 deep-link scenarios and none is an
AC-30 scenario.

### Clause-specific traps, and what was done about each

- **(a) the sample is taken before the append.** One append is evaluated from both
  samples and they must **disagree** — before → follow, after → not. The model takes the
  metrics as an argument, so it cannot be wrong about when the caller sampled; what this
  pins is which sample the AC mandates, and it goes red if the threshold is ever widened
  until it absorbs a message row. Who sampled when is device-tier, and is named as such.
- **(d) is a count.** Asserted as aggregation: after n arrivals the single affordance's
  label carries `n`. An implementation producing one pill per message could not report an
  aggregate. The literal node count is device-tier and is said so plainly rather than
  approximated.
- **(e) waiting vs arrived.** Six cases, none of which passes on the pill merely existing:
  the two NMA-NEW literals filled with the count; NMA-WAITING quoting the question head
  verbatim; a clarify head with typographic quotes; a *resolved* question falling back to
  NMA-NEW; a question **above** the fold that must **not** wait (a model scanning every
  message instead of the below-fold slice fails here); and the announcement path — an
  unchanged pill stays silent, the NEW→WAITING transition speaks.
- **(g) three scroll paths.** Three structurally different tests, one per trigger, per
  L-006 — never one parameterised over a shared setup. The doubles are built with
  `makeReduceMotion(true)` and **never** `set(true)`, because `set` also fires `onChange`
  and a test using it would prove "the controller reacts to a change notification" while
  the start-up read path went unasserted. Each case asserts the change listener never
  fired. The mid-session `set(true)` door is asserted separately so it can never stand in
  for the three.

## 5. Follow-ups

1. **mobile-agent — add three AC-30 scenarios to `.mobile-app/`** (`nma-new`,
   `nma-waiting`, `follow-at-bottom`) so TC-009's seven device steps can run.
   `.mobile-app/` is mobile-agent's tooling; qa-mobile-agent does not own it.
2. **Observation, not a bug — the headless surface has no scroll seam.** The public
   `Surface` API exposes no way to feed scroll metrics in, and `a11yIds()` never
   publishes `assistant-new-message-affordance` in any state reachable through it. The
   pill's own wiring lives one tier up, in an RN component and its hook, so off-device
   the affordance is reachable only through the follow model — which is exactly why
   (d)'s node count and (f)'s tap are device-tier in this run. Two ways to close that,
   and it is a design call, not a QA one: give `Surface` a scroll seam (one `scrolled()`
   input and the affordance in `a11yIds()`), which would move (d) and (f) into the
   vitest tier; or leave it as it is and treat follow-up 1 as the whole answer. Either
   way TC-009 stays, because visibility, overlay and frames need a device regardless.
