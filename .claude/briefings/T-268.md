# BRIEFING — T-268 (the voice button says "Start listening" and does not listen)

- **Task ID:** T-268 · **Module:** assistant · **Feature:** — · **Agent:** spec-agent · **Date:** 2026-08-23
- **Scope:** `docs/specs/`. Do NOT touch `docs/design/`, `src/`, or `.claude/tools/` — three agents are
  in flight on those trees right now.

## Context

Reported **independently by web-agent and mobile-agent in the same hour**, each having hit it while
building the FAB. Two implementers, one wall, same conclusion.

The drawing says `aria-label="Start listening"` (`app-shell-ios.html`). Both clients set exactly that
label — `src/assistant/mobile/components/VoiceFab.tsx:33` and `src/assistant/web/components/Chrome.tsx:84` —
and **both wire it to surface navigation** (`onGo` / `onGoTalk`), because **the model has no separate
"start listening" action.**

So a screen-reader user hears "Start listening", activates it, and the app changes screens without
listening. WCAG 2.5.3 territory, and more plainly a lie told to the one user who cannot see that nothing
happened. Neither implementer relabelled it quietly; both stopped and reported.

## The decision you are being asked to take

Either:
- **(a)** the label is wrong, and the control should be named for what it does (navigate to the talk
  surface); or
- **(b)** the control is right, and the model owes a "start listening" action the FAB can call — in
  which case the spec must say what that action is, what happens on arrival, and what the label becomes
  in each state.

**Check `F-002` and the mic-control entry in `components.md` for whether starting capture on arrival was
ever the intent** before you pick. There is prior art here; do not decide it fresh if the spec already
answered it and the clients simply did not implement it.

Whichever you pick, **write it once, in the spec**, so two clients cannot each pick their own answer —
which is exactly what almost happened.
